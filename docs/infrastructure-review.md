# Infrastructure review

Scope: the Terraform in `infra/` and the EC2 boot script. Nothing was applied: no AWS account, credentials or paid resources were used. "Verified" below means checked by tooling or by running the code locally; "Unverified" means it depends on real AWS behavior that could not be observed.

## Area by area

| Area | Assessment |
|---|---|
| IAM least privilege | Instance role: S3 object read/write/delete on one bucket, `ListBucket` on it for the readiness probe, `kms:Decrypt/GenerateDataKey/DescribeKey` on one key, `GetSecretValue` on three named secrets, ECR pull on one repository plus the unavoidable `GetAuthorizationToken` on `*`, log writes to one log group, and the SSM managed policy for Session Manager. No `DeleteObjectVersion`, no wildcard actions. Terraform itself needs broad rights to create the stack; that identity is out of scope. |
| VPC and subnets | Three tiers over two AZs. The data tier has no default route. The app tier reaches the internet through one NAT (a cost-driven single point of failure, noted in the docs). An S3 gateway endpoint keeps bucket traffic and ECR layer pulls off the NAT. The default security group has no rules. Flow logs capture rejected traffic only. |
| Security groups | Internet to ALB on 443 and 80 (redirect); ALB to app on 8000; app to RDS on 5432 and Redis on 6379 by security-group reference; app egress limited to 443 (internet) and the database ports inside the VPC CIDR. The 443-to-anywhere egress is the Trivy finding: replacing it needs interface endpoints for ECR, Secrets Manager and CloudWatch Logs plus a way to pull the Redis image. |
| RDS access | Private subnets, `publicly_accessible = false`, ingress from the app group only, `rds.force_ssl=1`, encrypted with the customer managed key, backups 7 days, deletion protection, master password created and held by RDS in Secrets Manager (not in Terraform state). The app connects as `docs_app`, created by `scripts/bootstrap_db_role.py` at boot. |
| S3 bucket policy | Public access blocked at four levels, ownership enforced, TLS-only deny, deny of `PutObject` without `aws:kms` encryption, versioning, SSE-KMS with bucket key, lifecycle for old versions. The application sets the SSE headers on upload (covered by the boot script settings `S3_SSE=aws:kms`). |
| KMS | Rotation on, 14-day deletion window. Key policy: account root (delegating to IAM, the AWS default), CloudWatch Logs service, and CloudWatch alarms. The last one was **added during this review**: alarms publish to an SNS topic encrypted with this key, and without it the alarm action fails silently. |
| Secrets Manager | App secret (JWT, app DB password, metrics token) generated by Terraform and read by the instance at boot; the RDS master secret is service-managed; the optional Redis token is a separate secret. Generated values do appear in Terraform state, so the state bucket must be encrypted and restricted. No rotation schedule for the app secret (rotation signs everyone out; handled by runbook). |
| ALB | HTTPS listener with `ELBSecurityPolicy-TLS13-1-2-2021-06`, HTTP redirected with a 301, `drop_invalid_header_fields`, deletion protection (variable), a listener rule that answers 404 for `/metrics`, `/docs` and `/openapi.json`, and health checks on `/health`. The hop from ALB to instance is plain HTTP inside the VPC. Optional WAF with managed rule groups, a per-IP rate rule and redacted logging. No ALB access logs. |
| CloudWatch alerts | ALB 5xx, unhealthy targets, EC2 status checks, RDS CPU and free storage, to an SNS topic with an optional e-mail subscription. The application metrics and alert rules live in Prometheus, which is part of the local stack only; the AWS deployment has no Prometheus or Grafana and `/metrics` is deliberately not reachable through the ALB. |
| TLS | Client to ALB: TLS 1.2/1.3 policy with an ACM certificate you provide. ALB to instance: plain HTTP. Instance to RDS: TLS required by the server; the client uses `ssl=require`, which encrypts but does not verify the server certificate (no CA bundle in the image). Instance to ElastiCache: TLS (`rediss://`) with certificate verification on by default in redis-py. S3 and AWS APIs: TLS. |

## Does the EC2 startup script start the application?

Reading the script against the files it generates found and fixed two defects that would have prevented a working deployment; running it found no others.

1. **Non-existent package.** `dnf install ... awscli` would fail (Amazon Linux 2023 ships AWS CLI v2 preinstalled and has no package of that name) and `set -e` would abort the boot. Removed.
2. **IMDS hop limit.** The API runs in a container behind the Docker bridge. With `http_put_response_hop_limit = 1` the IMDSv2 token response cannot cross the extra hop, so boto3 would never obtain the instance role's credentials: every upload and the readiness probe would fail while the ALB health check (which does not touch S3) still passed. Raised to 2, with the trade-off recorded in the threat model.

Two further defects were found in the application and compose layers while tracing the same flow: the host-header check rejected the ALB's health checker (every target would have been unhealthy), and the metrics token was optional in production. Both are fixed and tested (see [security-review.md](security-review.md)).

What `infra/tests/verify_user_data.py` demonstrates (and runs in CI on every infra change):

* the template renders for both topologies (with and without ElastiCache) and parses with `bash -n`;
* executed against stubs, the script exits 0 and performs, in order: ECR login, image pull, network creation, runtime-role bootstrap, migration, service start;
* no secret value appears in the user-data text (it only contains secret ARNs);
* the generated `api.env` loads into the application's own `Settings` with `ENVIRONMENT=production`, which enforces the weak-secret, wildcard CORS and host, docs and metrics-token rules;
* the API connects as `docs_app`; migrations use `docs_owner`; an RDS password containing `/ + = : @ # ? % & !` survives URL encoding;
* the env file is mode `0600` and the systemd unit starts a read-only, capability-free container with the CloudWatch log driver.

### Unverified AWS-specific behavior

None of the following could be observed without an account. Treat them as the first things to check on a real deployment.

* AWS CLI v2 and `python3` are present on the Amazon Linux 2023 AMI as assumed, and the Docker package name and service unit match.
* The ECR login and image pull succeed through the NAT, with layers fetched via the S3 gateway endpoint.
* The Docker `awslogs` driver works with only `logs:CreateLogStream` and `logs:PutLogEvents` granted (the log group exists, so `CreateLogGroup` is withheld).
* boto3 in the container obtains credentials through IMDSv2 with hop limit 2, and presigned URLs signed by temporary credentials behave as expected near credential rotation.
* The RDS-managed secret's JSON shape (`username`, `password`) and the asyncpg `ssl=require` option against RDS.
* The ElastiCache AUTH token and `rediss://` endpoint accept the connection with the Python image's CA bundle.
* The KMS key policy plus IAM is sufficient for RDS, Secrets Manager, ECR, SNS and CloudWatch Logs to use the key (RDS and ECR create grants through the caller).
* The WAF logging resource policy and managed rule group names (`AWSManagedRulesCommonRuleSet` and the other two) are accepted by the provider and service as written; `terraform validate` cannot check this.
* Alarm actions actually deliver to the encrypted SNS topic after the key-policy statement added in this review.
* `terraform apply` ordering (the ECR repository must exist and contain the image before the instance boots) works as described in [deployment.md](deployment.md).

## MinIO source-build strategy for local development

Why it exists: the project stopped publishing community container images, so the Compose stack cannot simply pull one.

What was verified: the upstream README (retrieved during this review) states that the repository is no longer maintained, that the community edition is distributed as source only, and that it is licensed under AGPL v3. The pinned commit builds and was exercised both locally and in GitHub Actions: the integration suite, including presigned-URL expiry and signature checks, passes against it.

| Concern | Assessment |
|---|---|
| Maintenance | No upstream security fixes will arrive. A pinned, unmaintained S3 server accumulates unpatched vulnerabilities. Acceptable only because it is a local development and CI test dependency, bound to `127.0.0.1`, holding no real data. It must never be used in staging or production; the AWS deployment uses S3. |
| License | AGPL v3 obligations attach to distributing or providing network access to modified versions. This repository does not copy MinIO code or ship its binaries or images: it contains a Dockerfile that downloads and compiles the source on the developer's or CI runner's machine. Using it unmodified as a test fixture is the low-risk case. Anyone redistributing a built image, or running it as a service for others, needs their own AGPL review. This is an engineering note, not legal advice. |
| Supply chain | `go install` resolves a pseudo-version from the Go module proxy, which is checksummed by the Go checksum database, but the build still compiles code that nobody maintains. The Dockerfile pins the exact commit; Dependabot does not track it. |
| Build cost | The first build takes several minutes. CI caches the binary keyed on the version. |
| Portability | The application only speaks the S3 API (`S3_ENDPOINT_URL`, path-style addressing). Any S3-compatible server works: SeaweedFS (Apache-2.0) and Garage (AGPL) are maintained alternatives; the test suite also runs against moto, so swapping the compose service for another S3 server is a change to one service definition. The real-expiry test is the one that needs a server that validates presigned signatures. |

Recommendation for a long-lived fork of this project: replace the compose service with a maintained S3-compatible server and keep MinIO only if a pinned, isolated test fixture is still wanted.
